# 历史消息分页与系统记录

`get_group_msg_history` 和 `get_friend_msg_history` 保留 `message_id` 分页，另支持 `history_cursor` 不透明分页游标。

请求中的 `count` 为 1–100，方向固定为较旧消息。`message_id` 与 `history_cursor` 不可同时指定。消息列表按精确原生序号升序排列，长整数不转为 JavaScript Number。普通消息的序号必须为唯一正整数；已识别系统灰条允许零序号，或与其他灰条、普通消息共享序号。每条记录始终以完整原生消息 ID 区分。

QQ `3.2.35-54395` 的原生含锚点查询使用 `reverse=true` 获取较旧记录；两个账号的只读方向探测已确认 `false` 返回较新记录。该布尔值属于原生接口语义，与 OneBot `reverse_order` 参数不同。未消费记录若越过已知正序号上界仍明确失败，不通过放松方向校验掩盖错误页。

返回字段：

- `messages`：可完整转换的普通消息；系统记录被过滤时数量可能少于 `count`，也可能为空。
- `next_message_id`：本次原始消费边界恰好是普通消息时的 OneBot ID；边界为系统记录时返回 `null`。
- `next_history_cursor`：包含原始消费边界的签名游标，可在下一次请求中作为 `history_cursor` 使用。整页只有已识别系统记录时仍可推进。没有消费记录时为 `null`。
- `has_more`：QQ 接入尚未提供可验证的结束标记，保持 `null`；不按过滤后列表长度猜测是否结束。
- `direction`：`older`。

不透明游标绑定账号实例、真实账号、QQ 会话、聊天对象和方向，15 分钟过期；worker 重启或会话变化后失效，客户端应重新从最新页或普通消息 ID 查询。游标按原生 ID 保留已消费记录，避免共享序号或零序号导致重复输出、分页循环；原生 ID 不按数值猜测时间顺序。一次游标链最多消费 1024 条原始记录、游标字符串不超过 64 KiB，达到上限时明确失败，不静默遗忘已消费记录；可从已知普通消息 ID 继续创建新链。较长游标建议使用 JSON POST 或 WebSocket 请求，避免 GET URL 长度限制。游标不等于消息 ID，不能用于查询单条消息、撤回或引用发送。

目前仅识别已审计形状：群记录，`senderUin` 为 `0` 或 `"0"`、`senderUid` 为空串、`msgType=5`、`subMsgType` 为 `8` 或 `12`，且唯一元素为 `elementType=8`。`grayTipElement` 允许空对象，或真实只读查询中确认的群、JSON、XML 系统灰条信封；其他元素负载必须为空，灰条外层字段和类型须匹配白名单。不解析系统正文、不伪造发送者、不生成普通消息、不分配消息 ID。未知灰条结构、多个或混合元素、私聊无作者记录仍明确失败，待真实样本验证后扩展。

历史页在独立事务中完成转换及引用定位，最终校验账号会话后只进行一次原子持久化。转换、会话校验或持久化失败时，不发布部分映射、不消耗消息 ID。查询期间若其他消息改动同账号映射，返回忙碌错误，客户端可重新查询；不会覆盖并发消息。

本实现有离线回归测试。真实 QQ 对灰条字段、分页边界与媒体查询的覆盖须以单独云端测试报告为准。
